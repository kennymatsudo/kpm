# Agent write access patterns

Research date: 2026-07-29. Sources are vendor documentation or vendor-owned source.

## Bottom line

Do not treat a developer's normal CLI setup as a portable, app-wide permission grant. The established pattern is a separate, explicit execution policy in the embedding app: a bounded workspace sandbox, a clear approval policy, and a product-owned credential connection. Provider defaults may be a useful starting point only when the provider explicitly supports loading them and KPM has not supplied higher-precedence overrides.

For KPM, keep the conversation-level write grant as the product decision. Make it the single, plain-language boundary the user sees. Translate provider denials, sandbox limits, and unavailable credentials into a small number of actionable states, rather than letting agent prose expose internal sandbox or token details.

## Claude Code and the Claude Agent SDK

- **Settings can be inherited, technically.** When Agent SDK `settingSources` is omitted, it reads the same user, project, and local filesystem settings as Claude Code; `~/.claude.json` and managed policy are always read. This means a user's `defaultMode` and permission rules can affect an SDK session unless the host supplies higher-precedence session options. [Claude Code features in the Agent SDK](https://code.claude.com/docs/en/agent-sdk/claude-code-features), [settings precedence](https://code.claude.com/docs/en/settings).
- **The embedding application can, and normally should, own the prompt.** The SDK's `canUseTool` callback is designed for an application to present a tool request, wait for the user's decision, and return it. Permission evaluation also honours configured denials before callbacks. Anthropic recommends beginning restricted and switching permission mode as trust builds; `bypassPermissions` is for a sandboxed or fully trusted environment. [Agent SDK permissions](https://code.claude.com/docs/en/agent-sdk/permissions), [user-input and permission callbacks](https://code.claude.com/docs/en/agent-sdk/user-input), [SDK quickstart](https://code.claude.com/docs/en/agent-sdk/quickstart).
- **Do not use the user's Claude subscription login as KPM's auth strategy.** Anthropic states that third-party developers building products with the Agent SDK may not offer Claude.ai login or rate limits, and should use a Console API key or supported cloud-provider credentials. Inheriting configuration is therefore distinct from reusing Claude Code/Claude.ai OAuth. [Legal and compliance](https://code.claude.com/docs/en/legal-and-compliance), [authentication](https://code.claude.com/docs/en/authentication).
- **Sandboxing is not a complete credential boundary.** Claude's Bash sandbox applies to Bash and child processes; built-in file tools, MCP servers, and hooks run on the host unless the app supplies a full sandbox/container/VM. It supports explicit credential-file and environment-variable deny/mask settings. [Bash sandbox](https://code.claude.com/docs/en/sandboxing), [sandbox environments](https://code.claude.com/docs/en/sandbox-environments), [sandbox credential settings](https://code.claude.com/docs/en/settings).

## Codex CLI and Codex SDK

- **Codex deliberately separates sandboxing from approvals.** The sandbox defines the technical boundary; the approval policy decides when a user must be asked. Its documented local auto preset permits reads, edits, and project commands inside the workspace, and asks when it needs network access or a write outside it. Network is off by default. [Agent approvals and security](https://learn.chatgpt.com/docs/agent-approvals-security), [sandboxing](https://learn.chatgpt.com/docs/sandboxing).
- **Personal Codex defaults can be shared across Codex surfaces.** Codex reads `~/.codex/config.toml`; the CLI and IDE extension share its configuration layers, including approval and sandbox settings. Project layers require workspace trust, and CLI or explicit `--config` overrides take precedence. [Config basics](https://learn.chatgpt.com/docs/config-file/config-basic).
- **But an embedding app can override or suppress that inheritance.** The TypeScript SDK wraps the Codex CLI, inherits the Node process environment by default, and lets the host replace that environment entirely, explicitly noting Electron-like sandboxed hosts. It also passes host `config` as CLI overrides. Thus KPM cannot rely on user defaults if it supplies its own environment or `--config` values. [Codex SDK source](https://github.com/openai/codex/tree/main/sdk/typescript), [Codex SDK documentation](https://learn.chatgpt.com/docs/codex-sdk).
- **Use app-server if KPM needs in-turn approvals.** Codex app-server sends JSON-RPC approval requests for commands and patches, and expects the client UI to present and answer them inline. That is the native route to a first-class KPM approval prompt instead of failing a write and retrying on the next turn. [Codex app-server](https://learn.chatgpt.com/docs/app-server), [app-server protocol source](https://github.com/openai/codex/blob/main/codex-rs/app-server/README.md).

## SDK-wrapper products

- **VS Code and Copilot SDK sessions keep a protected local boundary.** VS Code exposes session permission levels and scoped tool approvals. Its optional terminal sandbox defaults to read access for the workspace and its runtime temp directory, denies `$HOME` reads to protect SSH keys and credentials, and limits writes to the working directory. It adds narrowly needed read paths for common tools, including `~/.gitconfig` for Git. File tools are governed separately because the terminal sandbox does not cover them. [VS Code approvals](https://code.visualstudio.com/docs/agents/approvals), [VS Code trust and safety](https://code.visualstudio.com/docs/agents/concepts/trust-and-safety).
- **GitHub Copilot makes credential access an explicit elevation.** Copilot CLI's local sandbox defaults to the working directory and can reset its filesystem policy when the session ends. Its "Allow keychain access" setting is off unless the user enables it specifically for credentials used by Git and `gh` helpers. VS Code's Copilot CLI wrapper carries the editor's GitHub authentication context and prompts if extra GitHub permissions are needed; it does not require an agent to read `gh` configuration. [Copilot local sandbox configuration](https://docs.github.com/en/copilot/how-tos/cloud-and-local-sandboxes/configuring-local-sandbox-settings), [Copilot CLI sessions in VS Code](https://code.visualstudio.com/docs/agents/agent-types/copilot-cli).
- **Builder Fusion primarily avoids the credential problem through product connections and execution scope.** A Fusion project connects to a Git provider with access to selected repositories and normally sends changes as pull requests. Its project ACL checks AI `read`, `write`, and `list` operations, with an unmatched operation defaulting to deny. Users can choose cloud, local-machine, or local-container execution. Builder documents direct host execution for local-machine mode, but does not document a default host-home or credential-file deny-list there. [Fusion Projects](https://www.builder.io/c/docs/get-started-fusion), [Fusion ACL basics](https://www.builder.io/c/docs/acl-basics/), [Builder execution environments](https://www.builder.io/c/docs/desktop-app-execution-environments/).
- **Cursor separates interactive local work from cloud autonomy.** Its interactive Agent terminal can require confirmation, with auto-run opt-in; its CLI prompts for terminal commands, while noninteractive mode grants full write. Cursor's background agents instead run in an isolated cloud VM with a GitHub App grant, auto-run terminal commands, and network access. Cursor explicitly warns about prompt-injection and exfiltration risk in that mode. Cursor documents MCP OAuth and environment-variable authentication, but its public docs do not describe a protected-read list for `~/.ssh`, `~/.config/gh`, or Docker credentials. [Cursor modes](https://docs.cursor.com/en/agent/modes), [Cursor CLI](https://docs.cursor.com/en/cli/using), [Cursor background agents](https://docs.cursor.com/background-agent), [Cursor MCP](https://docs.cursor.com/context/model-context-protocol).
- **Lovable and Replit avoid host-file permission prompts by running inside a product-managed project environment.** Lovable's GitHub integration uses a GitHub App/OAuth connection and its secret UI keeps values hidden after entry. Replit's Plan mode is read-only until the user approves a task plan to enter Build mode; GitHub import and service credentials are product connections/secrets, not the developer's local CLI configuration. Their documentation does not describe local home-directory or Docker credential handling because these are not local-host execution products. [Lovable GitHub integration](https://docs.lovable.dev/integrations/github), [Lovable Cloud secrets](https://docs.lovable.dev/integrations/cloud), [Replit Plan and Build modes](https://docs.replit.com/learn/plan-vs-build-mode), [Replit GitHub import](https://docs.replit.com/build/import-from-providers).

The useful common pattern is not "trust the user's normal CLI defaults." It is either an isolated project environment or a local workspace boundary with an explicit elevation path, plus a product-owned Git provider connection. The closest direct comparison, VS Code, protects home-directory reads by default but admits narrow safe tool reads. Builder shows that path-specific read permissions can also be enforced independently of write permissions. No reviewed vendor documentation supports treating Claude Code or Codex personal defaults as an embedding application's security authorization.

## Credentials and GitHub

- **Do not pass a broad `GITHUB_PERSONAL_ACCESS_TOKEN` into agent commands by default.** A sandbox that correctly prevents access to the user's home or keychain will also prevent `gh` from reading its normal configuration. That is expected isolation, not a user error.
- **`gh` is designed around a credential store or an explicit automation token.** `gh auth login` stores a token in the system credential store when available, and falls back to a plaintext config file. For headless/automation use it supports `GH_TOKEN`/`GITHUB_TOKEN`; `GH_CONFIG_DIR` redirects configuration from the normal home-directory location. [gh auth login](https://cli.github.com/manual/gh_auth_login), [gh environment](https://cli.github.com/manual/gh_help_environment).
- **Products avoid this friction by owning the connection.** Claude's GitHub MCP example passes a fine-grained PAT as a server authorization header, while remote MCP uses OAuth and securely stores/refreshes tokens. Codex's GitHub review is set up as a Codex cloud repository connection rather than by asking an agent to discover a local `gh` token. [Claude Code MCP](https://code.claude.com/docs/en/mcp), [Codex GitHub review](https://learn.chatgpt.com/docs/third-party/github).

## Product recommendation

1. Keep KPM's explicit per-conversation write grant as the authority for direct file, shell, and git writes. It provides one consistent meaning across providers.
2. Default the agent runtime to a workspace boundary with no network and give a concise KPM approval only when it needs to cross that boundary. Keep targeted denies for secret roots (`~/.ssh`, keychains, credential stores, Docker credentials), but do not block ordinary developer configuration wholesale. Do not surface raw provider sandbox narration in chat.
3. Treat provider configuration as optional preferences, not authority: Claude SDK may load normal settings; Codex may load `~/.codex/config.toml`. Do not rely on either when KPM explicitly constrains the runtime.
4. Move GitHub reads and writes that KPM presents as a product feature through KPM's authenticated GitHub integration or an explicit, scoped user connection. Use `gh` only as an optional execution fallback and report one compact remediation state such as “Connect GitHub to read PR details.”
5. If in-turn Codex approvals are a priority, migrate the Codex integration to app-server. Otherwise document the current turn-boundary behaviour as a provider limitation, not a sandbox failure.
